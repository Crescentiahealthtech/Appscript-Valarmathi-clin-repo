This is an engineering assessment. It describes what the software does and does not do. It is not legal advice, and it does not decide whether the clinic is a Significant Data Fiduciary under section 10 — that is for a lawyer.

1Executive summary

Three critical failures, all of them now closed in code. Two facts were established during the work that need a decision from someone other than an engineer.

What the system is

The clinic runs on Google Apps Script: a web application whose database is a Google spreadsheet, whose documents are PDFs in Google Drive, and whose server code runs under one Google account. Under the Act the clinic is a Data Fiduciary and each patient is a Data Principal.

What was wrong

  1. The application answered anybody, as the owner. It was published so that no sign-in was required, and every server function ran with the owner's full access to the spreadsheet. 136 of those functions asked no question at all about who was calling — including the ward board with every inpatient's diagnosis, complete ward notes, full lab reports with results, live inpatient bills, insurance claim settlement, the cash drawers, and writes to clinical records. Patient IDs are sequential and printed as a barcode on every patient card, so the identifier needed to walk the register was public.
  2. Passwords were readable. Staff passwords sat in the spreadsheet in plain text. Patient portal passwords were worse: they were calculated — the first three letters of the name plus the year of birth — from information printed on the patient's own prescription, beside the barcode of the ID needed to use them.
  3. Patient documents were published to the open web. Lab reports and prescriptions were uploaded to Drive as "anyone with the link", and the link was sent over WhatsApp. Those links never expired, worked from every forwarded copy, and nothing listed them, so nothing could withdraw them.

Alongside those: no consent was ever recorded, there was no way to answer a patient's statutory request, no retention policy, no breach procedure, no record of who had read a file, and no processor agreements.

What changed

Every endpoint the browser can reach now establishes who is calling and what they are allowed to do. Passwords are stored as salted digests and a plain-text one is refused outright. Documents are private and reached through expiring, countable, revocable links. Consent is captured per purpose against a versioned notice and can be withdrawn by the patient themselves. Statutory requests have a register, a clock and a mandatory identity check. Breaches have a register that records the ones judged not notifiable, with reasons. Reads of clinical documents are audited, and an automated weekly review reads that audit for the patterns that precede a disclosure.

Two things are true today that were not known before this work

1. The records are held in a personal Gmail account. The spreadsheet is owned by crescentiahealthtech@gmail.com. A personal Google account carries no Data Processing Addendum, so section 8(2) is met for none of the clinic's patient data. It also has no administrative console: if that account is lost, recovered by someone else, or belongs to a person who leaves, the clinic's entire medical record goes with it.

2. The application was reachable without a sign-in for its whole life to date. Whether that period must be notified to the Data Protection Board and to every affected patient under section 8(6) is a legal judgement, not an engineering one. It needs to be made, and recorded either way.

What is left

Nothing in the remediation is finished until the web app is redeployed: the manifest change that requires a sign-in takes effect only on a new version. After that, four documents need adopting, two clinic decisions need making, and the move off the personal Google account needs starting.

N1 — why a new finding matters more than it sounds

The original assessment reported 62 unguarded endpoints. The true number was 136. The scanner read only the first 700 characters after each server call and took the last function name in that window, so any endpoint written after a long success handler was invisible — including registerPatient, an unauthenticated write to the patient master. It also stopped reading at the first code comment inside a call chain, which is how the function that rebuilds the lab database stayed hidden.

A compliance number you cannot trust is worse than no number, because it retires the problem in your head. The scanner was rewritten, and two further checks were added that did not exist: one that verifies the browser actually passes a session token in the right argument position (213 call sites), and one that exercises the password code against Node's own cryptography (31 assertions).

3How each change meets the Act

Six obligations in the Act cannot be met by writing a policy — the software has to do them. This is the mapping, with the reasoning behind the choices that were not obvious.

s.8(5) — reasonable security safeguards

Every endpoint now asks who is calling. One line at the top of each: crescRequire_(sessionToken, 'ward.read'). The permission vocabulary and the role matrix already existed in RBAC.gs; nothing new had to be designed, only applied — to 109 functions and 213 call sites.

Three problems had to be solved that a one-line guard does not describe:

  • Server functions call each other. The case sheet raises a lab order; the discharge settlement settles the credit bill. The inner call has no token to pass, so guarding it would refuse the clinic's own code — but leaving it open is no good either, because the browser can reach it too. A successful guard now remembers the caller for the length of one execution, and the inner guard checks its own permission against that same person. A nurse whose ward note raises a lab order still has to be allowed to order labs; she simply does not have to prove who she is twice. This is safe because Apps Script gives every call a fresh script context, so it cannot leak between users.
  • The lab status machine was split in two. Six internal callers drive it, each already guarded by what its own user is doing. Had they inherited the endpoint's permission, the accountant raising a lab bill would have been refused for not being a phlebotomist.
  • Eight endpoints answer without a session, and say why in the source. The sign-in steps, the password change, the clinic letterhead, the interface markup, the privacy notice and the public request form. An allowlist forces "this one is fine" to be defended once in writing rather than re-argued by whoever reads the file next.

Passwords. Stored as a salted, iterated SHA-256 digest and compared in constant time. Two deliberate refusals, both of which will look like inconvenience and are the point:

  • A plain-text password is refused at sign-in, not silently hashed. Hashing a password that has already been readable by everyone with the spreadsheet preserves the compromise instead of ending it.
  • Its owner cannot use it to change it either — that would hand the account to whoever copied it rather than to the owner. Only an administrator resets it.

This is not bcrypt, and the code says so rather than implying otherwise. Apps Script exposes no slow key-derivation function and cannot load one; iterated HMAC-SHA-256 is what the platform permits. The remaining defences are the account lockout, two-factor authentication, and the fact that a digest is useless to somebody reading the sheet.

s.8(5) and s.8(7) — documents

The file now stays private. The patient receives a link into the clinic's own application carrying a single-use key: it expires in fourteen days, counts how many times it is opened, closes itself after twenty-five, can be withdrawn in one click, and writes an audit row every time it is opened. The register stores only a digest of the key, so the spreadsheet — which far more people can open than should ever read a report — does not itself contain the means of access.

The old WhatsApp report link was withdrawn rather than repaired. It returned any order's complete lab report to anyone who asked, with no key and no session, and order numbers are sequential and printed on the patient's own paperwork. Anyone still holding such a message now gets a page saying the clinic will send it again.

ss.5, 6 and 9 — notice, consent, children

Registration now captures consent per purpose, against the version of the notice in force, in the same action that creates the patient. Three decisions worth understanding:

  • Care and billing are not tick boxes. They are recorded as legitimate uses under section 7, because a consent dialog must never be able to stop somebody being treated.
  • An unticked box is recorded as a refusal. "We never asked" and "they said no" are different facts and only one of them needs asking again. A system that stores only agreement cannot tell them apart.
  • Under-18 registration asks who consented and how they are related (s.9).

s.6(6) — withdrawal as easy as giving

This is the clause most systems fail. Consent is given at a desk in seconds; if taking it back means telephoning during working hours and persuading somebody, the section is not met. The patient's own portal page now carries their consent switches, their nominee and a request form.

ss.11–14 — rights, with a clock and an identity check

Every request carries a due date and the queue sorts overdue first. One function assembles everything held about a patient across eleven sheets, including the list of who it has been disclosed to, which is s.11(1)(b). Two additions matter more than they look:

  • A form the patient can reach — ?privacy on the web app, with no staff login. A form only staff can reach is a way of receiving fewer requests, not of answering them.
  • Verification is mandatory before a request can be closed. Answering an access request to the wrong person is a disclosure dressed as compliance, and the statutory right is precisely what an impostor would use to ask for it. A call back to the number already on the record is the cheapest check the clinic has and the one thing an impostor cannot arrange.

Nomination (s.14) is a separate append-only register, deliberately not the emergency contact already held: that was collected so somebody could be reached in a hurry, and was never given for this purpose. It is append-only because "who was nominated on the day they died" has one correct answer, and it is not "whoever the row says now".

s.8(6) — breach

An automated weekly review reads the audit log for the four patterns that actually precede a disclosure here: repeated failures against one account; failures spread across many identifiers, which is what walking the sequential patient IDs looks like; one person reading an unusual number of records in a day; and one shared document opened six times or more, which is what a forwarded message looks like.

The register holds the incidents judged not notifiable, with the reason and the named person who decided. In an inquiry that is the only thing that shows the clinic was looking. The software refuses to record a decision without a reason, because "not notifiable" is the one that will have to be justified.

s.8(7) — retention

The retention report deletes nothing, on purpose: a medico-legal case or an insurance dispute can require a record years after its ordinary period, and a sweep that deletes on its own is how a clinic loses the file it is about to be asked for. What is deleted automatically is only what nobody could ever need — expired links, dead sessions.

The single exception erases education, occupation and marital status. Nothing in the codebase ever read them, so under s.6(1) there is no purpose to state and no upside to weigh against erasing them. They have also been removed from the registration form, the profile editor and the patient search.

s.8(2) — processors

Documented in full, including the finding that the records sit on a personal Google account with no Data Processing Addendum. WhatsApp's consumer terms are not a processor agreement either; the clinic either moves to the business API with a contract, or relies on the patient's specific consent and says in the notice that the message goes through Meta.

4How to run anything in the Apps Script editor

The single most common reason a runbook stalls. Two behaviours of the editor are not obvious, and one of them is dangerous.

Where the files are

  1. Open the spreadsheet → Extensions → Apps Script.
  2. The left-hand panel lists every file. .gs files hold the server code; .html files hold the screens.
  3. Click a file to open it. The editor searches only the open file — Ctrl/Cmd+Shift+F searches all of them, which is how to find a function whose file you do not know.

The two things nobody tells you

1. The Run dropdown only lists functions in the file that is open

The dropdown beside Run and Debug is not a search of the whole project. If you cannot find a function there, you have the wrong file open. §5 gives the file for every function by name.

2. The Run dropdown cannot pass arguments — and here that is a live hazard

Whatever you select is called with no arguments. For two functions in this system that is the difference between a rehearsal and an irreversible change:

crescMigrateCredentials(true)   ← the DRY RUN: reports who would be reset
crescMigrateCredentials()       ← RESETS EVERY PASSWORD IN THE CLINIC

The dropdown can only ever perform the second. This is why RUN_Setup.gs exists — see below. Do not run the underlying functions directly unless you have read this paragraph and meant it.

The runbook file: RUN_Setup.gs

Rather than hunting through six files, open RUN_Setup.gs once. It contains the entire deployment sequence as numbered, argument-free functions, so the Run dropdown reads as a list of instructions in order. Destructive steps are split into a _DRYRUN_ and a _FOR_REAL_ so neither can be reached by accident.

Every name in that file ends in an underscore. In Apps Script that makes a function unreachable from the browser while the editor lists it normally. Without it, the file would have published "reset every password" and "mint an administrator session" as endpoints anyone with the web app URL could call by name — which the project's own scanner caught the moment the file was added.

Running one, and reading the answer

  1. Open RUN_Setup.gs.
  2. Choose the step from the dropdown at the top.
  3. Press Run. The first time, Google asks for authorisation — approve it as the account that owns the spreadsheet.
  4. The answer appears in the Execution log panel underneath. If you close it too soon, it is still there: left panel → Executions (the ⏱ icon) → click the run.

Copy the log from step 7b before you close it. That one prints the temporary passwords, and it is the only copy that will ever exist. Nothing — not the script, not the spreadsheet, not Google — can show them again.

6Before you start: the three things that can hurt

None of these is a defect. All three are consequences of doing the remediation properly, and all three are much cheaper to know about in advance.

1. Between pasting the code and running step 7b, nobody can sign in

A plain-text password is refused from the moment the new sign-in code is in place. That is what a forced reset means — it is the mechanism, not a side effect. The gap lasts only as long as you take to run step 7b, and the Apps Script editor does not need the web app login, so you cannot lock yourself out of fixing it.

Do not deploy at the start of a clinic session. Evening or a closed day.

2. Take a spreadsheet snapshot before step 7b, or rollback becomes painful

If you later revert the code but the passwords have already been hashed, the old sign-in compares plain text against digests and nobody can get in. Passwords cannot be recovered — that is the point of hashing them.

So, before step 7b: open the spreadsheet → File → Version history → Name current version → call it Before DPDP migration. Restoring that version restores the old column B.

3. Patients will need a Google account to open a document link

Requiring a sign-in is what closes finding C1, and it applies to the whole web app including the page that serves a report. Most patients on a smartphone have a Google account and will not notice; some will telephone. Worth briefing reception before the first report goes out, and worth weighing against the alternative, which is the report being readable by anyone the message was forwarded to, for ever.

When somebody leaves, disabling their login is not enough on its own. 9Decisions and questions for the lawyer

Software cannot decide any of these. Each one changes what the clinic tells patients.

Three decisions for the clinic

DecisionWhat turns on itWhere it is recorded
Voice typing Dictation sends the audio of a clinician describing a patient to Google's or Microsoft's speech service. Allowed clinic-wide, or forbidden. Privacy → Posture, or step 91. Then the matching paragraph in the consent notice — both are drafted.
WhatsApp Either a business-API contract, or reliance on each patient's specific consent plus telling them in the notice that the message goes through Meta. docs/PROCESSORS.md and the consent notice.
Google Workspace Whether section 8(2) is met at all, and whether the clinic or one individual controls the records. docs/PROCESSORS.md has the migration steps.

Four questions for the lawyer

  1. Is the period of anonymous deployment a reportable breach under s.8(6)? The application was published so that no sign-in was required, and 136 endpoints answered anyone with the URL, including ones returning diagnoses and full lab reports. Whether that requires notifying the Board and every affected patient depends on how widely the URL was distributed, which is a question of fact the clinic can answer. Whatever is decided must be recorded in the breach register with its reasons — including a decision that it is not notifiable.
  2. Is the clinic a Significant Data Fiduciary under s.10? If so it needs a Data Protection Officer, an independent audit and a data protection impact assessment. The assessment itself should be in writing either way.
  3. What is the correct inpatient and medico-legal retention period under the applicable state Clinical Establishments rules? The schedule uses three years for outpatient records, per the NMC Ethics Regulations, and marks inpatient and medico-legal as take advice.
  4. Does the consent notice say enough, and in the right languages? It is drafted in English and must be given in Tamil as well — s.5(3) gives the Data Principal the right to the notice in any language in the Eighth Schedule. A notice in English only is not a notice given to a patient who does not read English.

What the software can and cannot assert

It can prove: what consent was recorded, against which version of which notice, when and by whom; who read which document and when; what was shared with a patient and how often it was opened; when a statutory request arrived, how the requester was identified and what was done. That is the evidence base s.6(10) and s.8(6) require.

It cannot prove: that the notice was actually read aloud, that the person at the desk was who they said, that a deleted record was deleted everywhere including Google's backups, or that a document already downloaded has not been forwarded. Those are procedural, and the four documents in docs/ are where the clinic commits to them.

10Limits of this work

Stated plainly, because a remediation report that reads as complete is the most dangerous document in a compliance file.

  • Nothing was executed. There is no way to run Apps Script outside Google, so behaviour was not observed. What stands in for it: ten static checks, an audit that every one of 213 call sites passes a session token in the correct argument position, and 31 assertions against the password code using Node's own cryptography. Do the smoke tests in §7 before a clinic session, not during one.
  • 140 functions still carry no permission check. None of them is called by any screen in this project, but Apps Script exposes every server function to anyone who knows its name, so they are a smaller hole rather than none. node tools/rbac.js lists them; work them down when those files are next touched.
  • The password hashing is weaker than bcrypt because Apps Script provides no alternative. The lockout, two-factor authentication and the digest itself carry the rest.
  • A document link is a capability, not an identity. Whoever holds the link can open the document, exactly as before — but now it expires, is counted, is revocable and is one document rather than a permanent window. Authenticating the patient properly means the portal.
  • There is no SMS gateway, so a one-time code to the registered mobile is not possible yet. It is the right answer both for the portal credential and for verifying who is making a statutory request.
  • Erasure cannot reach Google's backups, nor a PDF a patient has already downloaded, nor a WhatsApp message already forwarded. Answers to patients should say so rather than promise an erasure the clinic cannot perform.

docs/DPDP_READINESS.mdThe full technical assessment, finding by finding, kept current with the code.
docs/CONSENT_NOTICE.mdThe notice given to patients. Has blanks and two marked decisions. Needs translating.
docs/RETENTION_SCHEDULE.mdEach record type, its period, its legal basis and who decides to delete.

docs/PROCESSORS.mdEveryone who touches the data, the record of processing, cross-border transfer.

Those five files plus this debrief are the clinic's compliance file. They live in the repository so that they change when the code changes; a compliance document that drifts from the system it describes is worse than none, because it is believed.
